# ADR-001: 页面配置使用现有 KV 的分离版本文档

## 状态

Accepted — 用户已确认页面管理设计。实现与验证状态以[验证记录](../reviews/2026-10-16-page-management-verification.md)与 CHANGELOG 为准（当时的实施计划原存于 `docs/superpowers/plans/`，该目录已于 2026-10-19 清理）。

## 日期

2026-10-16

## 背景

站点是单人博客，需要 About 正文、逐页模板设置、自建内容页和导航管理。现有 `site_setting` 为 MySQL/SQLite/H2 共有 KV 表；全局设置接口只处理少量白名单字段且对外全部公开。直接往全局设置添加草稿或大正文会混淆权限，也不能满足“保存草稿不影响线上”。

## 决定

由独立 PageService 管理 `page.draft.*`、`page.published.*`、`page.slug.*` 和独立导航行，不修改 schema，不扩大全局设置公开白名单。

- 草稿与公开快照分行；公开读取不会回落到草稿。
- 用包含 revision 的完整旧值作为数据库条件更新谓词。每次写入增量 revision，避免仅依靠单进程锁；不存在行的并发创建通过主键冲突返回409。
- slug 使用独立唯一 KV 主键预留，既保护未发布地址，也保护多个窗口同时创建。
- 公开摘要去掉正文，单页读取正文；所有配置走受控字段和样式白名单。
- MySQL TEXT 字段限制促使每份 JSON 限为48KiB UTF-8，正文10000字符，留出编码与扩展余量。

## 考虑过的替代方案

1. 在全局设置里放一个 pages JSON：不需要新实体，但会公开草稿、全站写冲突严重，单行容量也更容易触顶。
2. 新增页面/版本/导航表：适合大型 CMS 和无限历史版本，但本批需求不需要，且与保留既有 schema 的约束不符。
3. 单 JVM synchronized：不能保护多进程和数据库竞争，不作为版本检查的依据。

## 后果

备份必须包含全部数据库 KV，不只是网站设置 API 返回值。公开数据不能进入管理草稿缓存；恢复配置时需要保留 schemaVersion/revision。正文长度有明确上限，不把此功能扩展成任意文件库或无限版本系统。

当前 H2 和隔离 SQLite 可验证事务与行为；SQL 使用各数据库共有的绑定条件更新语法，但没有因此宣称真实 MySQL 环境已经验证。
